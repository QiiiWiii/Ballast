# 前端产品与交互架构

Ballast 前端定位为运营人员持续值守的机构执行工作台，不是交易所行情终端，也不是策略回测实验室。页面的首要任务是让 operator 快速回答四个问题：什么任务需要处理、执行到哪里、依据是什么、系统是否仍处于安全边界内。

## 外部项目调研结论

- NautilusTrader 不提供正式 Web 控制台，开源范围聚焦事件驱动执行内核、适配器与研究到实盘的一致性。Ballast 借鉴其“执行事实来自领域事件”的边界，不复刻不存在的 UI。
- barter-rs 同样不提供产品化前端，只暴露可供外部 UI 消费的状态副本、审计流和命令入口。Ballast 因此保持 Rust 为事实源，React 只展示 API/WS 返回的状态。
- Hummingbot 旧 Dashboard 采用 Streamlit，页面覆盖凭证、策略配置、回测、部署、实例、组合和表现，但官方已标记为不再主动维护。它适合作为功能清单参考，不适合作为交互和视觉基线。
- Hummingbot 的后继项目 Condor 使用 React，并将对象组织为 Agents、Bots、Executors、Portfolio、Reports 和 Settings。Ballast 借鉴其“对象列表 → 创建 → 详情 → 报告/设置”的工作流，但以 execution 为中心，不引入 agent 或 bot 概念。

## 信息架构

```text
执行工作流
├── 控制舱：异常、暂停、截止时间和通道健康
├── 执行任务：任务 blotter、筛选、创建和证据详情
├── 策略中心：共享模板、不可变版本和使用入口
└── 审批队列：live 能力开放后处理双角色审批

数据与通道
├── 执行分析：质量与运营效率
├── 市场与通道：五家交易所能力、标的和连接状态
└── 账户与对账：只读私有数据开放后的事实核对

安全与系统
├── 风险控制
├── 双腿对冲
├── 系统状态
└── 后续能力
```

交易所不是五个重复的一级产品页面。它是任务和策略的执行通道，也是市场与通道页的筛选和详情维度。

## 视觉与交互原则

- 固定深色侧栏代表控制平面；浅色工作区承载数据和证据。
- 页面不使用渐变统计卡、交易所品牌色或装饰性行情图。
- 桌面端优先宽表格和密集状态行；移动端优先任务卡片化阅读和底部工作流导航。
- 状态同时使用文字、形状和颜色，不允许只依赖颜色。
- 唯一标志性元素是居中零轴的“龙骨稳定轴”。纸面阶段固定表示执行残余；只有账户快照和成交对账可靠后才可表示净敞口。
- 后端失败时明确显示错误，不注入演示数据或静默 fallback。

## 核心页面职责

控制舱按严重程度排序：请求或链路错误、需处理任务、暂停与临近截止任务、通道状态，最后才是完成比例和滑点摘要。不同资产和数量单位不得汇总为一个总金额。

执行任务页使用 blotter 表达 ID/状态、交易所标的、方向和算法后端、目标与已执行、进度、残余、下一切片和证据入口。详情页继续展示计划/实际、盘口摘要、切片和领域事件。

策略中心管理模板而不是运行实例。模板版本不可变；创建任务必须先选择版本。venue-native 算法生命周期不得伪装成 managed IOC 切片。

市场与通道页统一横向比较五家交易所。无活跃订阅时显示未订阅，不得显示为已连接。
